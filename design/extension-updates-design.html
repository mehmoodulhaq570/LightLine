Updating Installed Extensions Approved with all recommendations 2026-11-25; built

Follow-up to design/own-extensions-design.html. Today an installed extension never changes: when LightLine's list or Zed's registry pins a newer version, the panel doesn't say so and there's no way to take it short of uninstalling and installing again. Panel crops are at real size in the default dark theme. Dashed green outlines mark what's new, and the red one marks a bug in today's panel.

What the user sees

Versions are examples. The arrow and the new version are one short ExtTextOut each, drawn only on rows with an update. When the name is long, the version gives way before the badge, as it does today.

How it works

1 · Know both versionsThe installed version comes from the extension's own extension.toml (the scan already reads it) and is kept in its own field. The available one is the list's version for an entry LightLine pins, otherwise the Zed registry's.
That fixes today's row, which showed the registry's version as if it were installed.
2 · Compare when a list arrivesA row has an update when the available version is newer by number (1.10.0 > 1.9.2, the comparison requires already uses). An older or equal one is never offered.
On opening the panel, as today, and on Check for Updates, which now refetches both lists instead of reusing them for 10 minutes.
3 · Update like an installThe same path: staged download, checks, backup, swap, rollback on failure. Then whatever the extension was doing is picked up again.
Update All does them one after another (installs already queue on one lock), with one status line: Updating 2 extensions (1 of 2)...

After an update, by kind

KindWhat happens
Color themeIf it's the theme in use, it's applied again by its variant's name, so the new colors show at once. If that variant is gone in the new version, LightLine Midnight is used and the status bar says so.
Icon themeIcons are reloaded, as after an install.
SnippetsThe cached snippets are dropped and read again on the next Ctrl+Space.
CheckerIts server restarts in the open files. A program LightLine downloaded for it is kept if the version it needs is unchanged.
LanguageThe grammar is rebuilt in the staged copy. If Windows still has the old grammar open (a file of that language was open), the swap fails, the old copy stays, and the status bar says Restart LightLine, then update Lua.

Speed and privacy

MeasureEffect
Startup, idleNone. Nothing is checked at startup or on a timer: the network is used only when you open Extensions, press Check for Updates, or press Update.
Opening ExtensionsWhen a list arrives, a version comparison for each installed extension: a handful of string splits, far below a millisecond.
Panel paintOnly rows with an update draw the arrow and new version; the header draws one more short label when there are updates.
Typing and scrollingNot touched.

Decisions for you

QuestionOptionsRecommendation
When to look for updatesOnly when you open Extensions or press Check for Updates · also once a day at startupOnly when you act. That's LightLine's privacy promise (no network the user didn't ask for), and it keeps startup at no work.
Where updates showInstalled rows + the header's count · also a dot on the Extensions icon in the railRows and header. Updates are only known once the panel has been opened, when you're already looking at it, so a rail dot would add little.
Update AllIn the header and the ··· menu · menu only · noneBoth. The header link shows only with two or more updates, so one update has one button.
A new commit without a new versionNot offered · offer it too (LightLine would record the installed commit)Not offered. The version is the promise: Zed's registry requires a bump for every change, and lightline-extensions' CONTRIBUTING does too.
Language whose grammar is in useTry, and keep the old copy with a "restart first" message if Windows holds it · always ask to restartTry first. Most of the time no file of that language is open and the update just works.
