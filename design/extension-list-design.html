LightLine's Own Extension List Approved and built 2026-11-24

Part 3 of “Fill the extension gaps without our own marketplace” (.claude/session.md). Drafted 2026-11-24. The panel crops below are drawn at real size (sidebar 286 px, 62 px extension rows) in the default dark theme. Dashed green outlines mark what's new.

A plain TOML file in the LightLine repo lists the extensions we've tested with LightLine, and later ones we write ourselves. The Extensions panel shows them first, with a LightLine badge, and already knows their name, what kind they are and a real description. Today a registry result only says “install to see whether LightLine supports it yet”. Nothing runs on a server. Anyone can propose an entry with a pull request, and we review it the same way as code.

What the user sees

Versions and descriptions in the crops are placeholders. The real ones come from each entry. The badge is one short rounded rectangle plus one ExtTextOut, drawn only on listed rows.

The file

It lives at registry/extensions.toml in the repo. That's not extensions/, which would look like installed extensions next to src/extensions/. There are two kinds of entry:

# LightLine's own extension list: extensions tested with LightLine.
# Propose one with a pull request; CONTRIBUTING.md says what's checked.
format = 1

[[extension]]               # 1. A Zed registry entry we've tested.
id = "catppuccin"
from = "zed"                 #    Installs Zed's pinned commit, so it updates when Zed's does.
name = "Catppuccin"
kind = "color-theme"         #    color-theme | icon-theme | language | snippets | checker
description = "Soothing pastel themes: Latte, Frappé, Macchiato, Mocha"
publisher = "catppuccin"
recommended = true           #    shown under RECOMMENDED; false = only found by search

[[extension]]               # 2. An extension of our own (or vetted), in its own GitHub repo, Zed's format.
id = "lightline-todo-snippets"
repository = "https://github.com/<owner>/lightline-todo-snippets.git"
commit = "92f46057151693648bd3acac1e0c138696f34433"   # 40 hex; updating it = a PR
version = "1.0.0"
name = "TODO Snippets"
kind = "snippets"
description = "TODO, FIXME and NOTE comments with your name and the date"
publisher = "LightLine"
requires = "0.13.0"             # hidden in older LightLine builds
  • Same ids as Zed's registry. If an id appears in both, our entry wins: it's the tested one. Our own extensions get ids that Zed doesn't use.
  • The installer stays the same. An own entry passes repository and commit straight to installer::install, which skips the GitHub contents API (one fewer request). A from = "zed" entry goes through today's zed_registry::resolve. After the download, the check of what the extension really contains still runs, so a wrong kind in the list can't install something LightLine can't use.
  • Prettier and Material Icons move into the file. Prettier keeps its built-in Turn Off behaviour (kind = "formatter", builtin = true). Then the three hard-coded Extension structs in app.rs, FEATURED, and the material-icons → material-icon-theme alias can all go.
  • Unknown fields and kinds are skipped, not errors. So an older build reading a newer list still shows whatever it understands.

How it gets to the app

1 · Built inThe file is compiled in with include_str!, so it doesn't touch the network.
Parsed the first time the Extensions panel opens, before its first paint. It's a few KB, read once.
2 · Fetched with Zed's listDownloaded from raw.githubusercontent.com/…/LightLine/main/registry/extensions.toml.
This happens on the same trigger that already fetches Zed's extensions.toml (opening the panel or ⟳), with the same 10-minute reuse. It adds no new trigger.
3 · MergeThe fetched copy replaces the built-in one if it parses and its format is one this build knows. Otherwise the built-in copy stays, silently.
Entries are merged into App::extensions by id, the same way as WorkerMessage::ZedRegistryList.

Fetching means a new tested entry reaches users without waiting for a release. Building the list in means it works offline and on first open. Privacy is unchanged: the network is used only when the user opens Extensions, as today.

Keeping it trustworthy

  • A CI test reads the file in the repo (an ordinary cargo test, so CI runs it). It checks:
    • the file parses;
    • ids are unique;
    • every repository is https://github.com/…;
    • every commit is 40 hex characters;
    • every kind is a known kind;
    • no entry has a path (a folder inside another repository);
    • descriptions fit the 62 px row.
    A bad pull request fails CI before anyone has to read it.
  • An ignored live test (cargo test --lib lightline_list -- --ignored) installs every entry into a temp folder and checks that each one really is the kind it claims. Run it before merging a list change, and before each release.
  • Pinned commits only. An own entry changes only through a PR that changes its commit. A from = "zed" entry follows Zed's pin, which Zed reviews.
  • What gets reviewed (goes in CONTRIBUTING.md): works in the latest release; no network or process use beyond what its kind allows (a checker's program comes from tool_download.rs's pinned list or PATH, never from the extension); a license that allows redistribution; a description written for LightLine, not copied from VS Code.

What to list first

A list is only worth showing if it has real entries in it. The first version would have no extensions of our own: only Zed entries we test. That moves today's hard-coded Featured trio into data and fixes the “install to see” problem for the extensions people want most:

KindEntries (each one tested before it's listed)
Icon themematerial-icon-theme
Color themesdracula, catppuccin, plus 2–3 more popular ones that render correctly through color_theme_adapter
Snippetspython-snippets, rust-snippets, react-snippets, fastapi-snippets, comment-block-snippets
Checkerstypos, codebook, harper (the three with a pinned download in tool_download.rs)
FormatterPrettier (built in)

Our own extensions come later, each through a PR once it exists. The first candidates are kinds that Zed's registry is thin on, such as snippet packs for LightLine's own languages and themes.

Work involved

  • Library: new src/extensions/lightline_list.rs (parse, validate, fetch with reuse, merge rules) and its tests; registry/extensions.toml.
  • UI:
    • app.rs: Extension gets listed and recommended fields; the hard-coded entries are removed.
    • extensions_panel.rs: the RECOMMENDED section, the two search headers, list entries sorted first, the new chips.
    • render/extensions.rs: the badge.
    • panels.rs: the worker message.
  • Docs: USER_GUIDE.md (Extensions), CONTRIBUTING.md (proposing an entry), docs/extension_implementation_plan.md, README feature line, CHANGELOG.md.
  • Done as one PR, then a live check against these crops, as usual.
