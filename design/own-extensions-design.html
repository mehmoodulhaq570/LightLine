LightLine's Own Extensions Approved with all recommendations 2026-11-25; built

Phase 3c of docs/extension_implementation_plan.md. The repository now exists, empty: mehmoodulhaq570/lightline-extensions (public, so LightLine can fetch from it). This page proposes what goes in it first, how it's laid out and checked, and the one LightLine change needed to install from it. Panel crops are drawn at real size in the default dark theme, and dashed green outlines mark what's new. The open choices are in Decisions for you at the end.

Where the gaps are

  • LightLine has one theme of its own, LightLine Midnight, and it's dark. There's no light theme and no high-contrast theme unless you install someone else's. Windows users with light mode or low vision have nothing made for LightLine.
  • Zed's registry has no C or C++ snippet pack. It has Python, Rust, Go, JavaScript, TypeScript and React packs, all already on LightLine's list or available to it. C and C++ are LightLine run languages, with ▶ Run beside main, and they have nothing.
  • Everything else LightLine can install (icon themes, checkers, language grammars) is well covered by Zed's registry, or needs work that isn't about content. LightLine already draws its own built-in file icons, for example.

So the first two extensions fill those two gaps. Neither one runs code, so neither needs WASM.

What the user sees

Extension 1 · LightLine Themes

A color theme extension with two variants built from Midnight's palette, so LightLine's chrome keeps the same feel in each. After install they're listed in the color theme picker like any other installed theme. Midnight stays built in and isn't in the pack (see the decisions).

Daylight keeps every code color at 4.5:1 or above (WCAG AA), including on the caret line, where the lowest is comments at 4.8. Its line numbers are deliberately quieter, at 3.6, which is above the 3:1 minimum for non-text UI. Contrast keeps every role at 7:1 or above (AAA). The repository's CI checks these ratios, so a later color change can't quietly drop below them. Midnight's macro color, 4.6, is the closest to the line today and isn't part of this work.

// themes/lightline-themes/themes/lightline.json
{
  "$schema": "https://zed.dev/schema/themes/v0.2.0.json",
  "name": "LightLine Themes", "author": "LightLine",
  "themes": [
    { "name": "LightLine Daylight", "appearance": "light",
      "style": { "editor.background": "#ffffff", "editor.foreground": "#1e293b", …
                 "syntax": { "keyword": { "color": "#1f5fd1" }, … } } },
    { "name": "LightLine Contrast", "appearance": "dark", … }
  ]
}

Only Zed keys that color_theme_adapter already maps are used, so nothing in LightLine's theme code changes. Every role is set explicitly rather than derived, so the chrome looks exactly like these previews. The live check compares a capture against them.

Extension 2 · C and C++ Snippets

One pack with two files, snippets/c.json and snippets/c++.json (Zed's language names; LightLine already maps .c .h and .cpp .hpp .cc to them). VS Code's snippet format, as for every pack LightLine reads. About 20 each, chosen for what people type in a run-it-now C or C++ file:

C (.c, .h)C++ (.cpp, .hpp, .cc)
main maina (argc/argv) inc incl (local) guard (include guard) func if ife for fori while do switch struct tstruct (typedef) enum printf scanf malloc (NULL check) fopen (error check) main maina inc once (#pragma once) ns class struct forr (range for) fori if ife cout cin vec map uptr (make_unique) lambda tmpl (template) try test (a minimal assert check)

House style: indentation written as \t (the format's convention), placeholders in the order you'd fill them, $0 at the natural end, and no using namespace std;. The live check confirms how a \t body comes out with insertSpaces on and off before the pack is published.

  • Folders by kind, each extension in Zed's own format. Any of them can be submitted to Zed's registry later with path = "themes/lightline-themes", without moving anything.
  • Ids start with lightline-. No Zed registry id does today, so ours can never collide with one, and it's obvious whose they are.
  • Each extension has its own version. Changing one extension doesn't touch the others' versions.

How LightLine installs one

LightLine's list gets an optional path. An entry with one installs only that folder, and everything after the download stays exactly as today.

# registry/extensions.toml (LightLine repo)
[[extension]]
id = "lightline-themes"
repository = "https://github.com/mehmoodulhaq570/lightline-extensions.git"
path = "themes/lightline-themes"      # new: relative, "/" only, no "..", no drive
commit = "<40 hex>"
version = "1.0.0"
kind = "color-theme"
name = "LightLine Themes"
description = "Daylight and Contrast, made to match Midnight"
publisher = "LightLine"
recommended = true
requires = "0.13.0"                   # older builds don't know "path": hide it from them
1 · Fetch only the foldergit init, sparse-checkout set --no-cone /themes/lightline-themes/, fetch --depth 1 --filter=blob:none of the pinned commit, checkout.
Only that folder's files are downloaded, a few tens of KB. Needs git 2.27 or later; an older git gets a clear error naming the version.
2 · Check, as todayvalidate_download runs on staging/<path>: manifest id matches, theme JSON or snippet files are valid.
A wrong kind or a broken file is refused before anything is moved.
3 · Promote, as todayThe folder moves into %APPDATA%\LightLine\extensions\lightline-themes, with backup, rollback and the exclusive lock unchanged.
The installed copy looks exactly like a whole-repo install, so nothing else in LightLine knows the difference.

The same change lets Zed registry entries with a path install, which zed_registry::check_installable refuses today. That includes Zed's own html, glsl and proto, which live inside its very large main repository. Their kinds still have to be ones LightLine supports. This is a side benefit, not a goal of this work.

Keeping it trustworthy

  • scripts/check.py in the extensions repository, run by CI on every push and PR (Python's standard library only: tomllib, json):
    • every extension.toml parses; the id equals its folder name, starts with lightline- and is unique; the version is x.y.z;
    • every file it names exists; theme and snippet files are valid JSON;
    • themes: each variant has a name, an appearance, and every role LightLine reads; text and syntax colors meet the ratios above (4.5:1 for light, 7:1 for contrast);
    • snippets: each has a prefix and body; no prefix appears twice in a file; placeholders are well formed.
  • In LightLine:
    • a unit test with a local fixture repository holding two extensions in subfolders (install one, check only its files arrive);
    • path validation tests, lenient in parse and strict in problems;
    • the existing ignored test, cargo test --lib lightline_list -- --ignored, which installs every list entry, now including these two from the real repository.
  • Pinned commits only, as for every list entry. A change to an extension reaches users only through a LightLine PR that moves its commit. Because LightLine fetches the list from main when the panel opens, that doesn't need a LightLine release.

Changing an extension later

1 · EditChange the files and bump version in that extension's extension.toml. PR to lightline-extensions; CI runs check.py.
2 · PinA one-line PR to LightLine moving the entry's commit and version. LightLine's CI checks the list; run the ignored install test before merging.
3 · Reach usersThe next time someone opens Extensions, the fetched list shows the new version.
Installed copies don't update themselves: LightLine has no Update button yet (see the decisions).

Speed and privacy

MeasureEffect
Startup, idleNone. Nothing new runs until the user installs something. Installed, a theme is applied exactly like any other installed theme. A snippet pack is read on the first Ctrl+Space in its language, as today.
Typing, scrolling, paintingNot touched. Themes change colors only, through the roles LightLine already paints.
InstallFaster than a whole-repo install: only the extension's folder is downloaded, not the other extensions beside it.
PrivacyUnchanged. The network is used only when the user opens Extensions or presses Install, and only to GitHub, as today.
